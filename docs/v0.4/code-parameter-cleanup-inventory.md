# v0.4 code and parameter cleanup inventory

## Baseline and scope

This audit is based on `76420d9eccc2fa71b54484e413951e040feba862`, the `develop` merge of `60859f5e1591411689bfe3efd04977aa1d3fe094` and the directly based, independently reviewed `e55fe768b0ffd1def5522a782f707de048284539`. The merge tree is identical to the reviewed feature tree. [Feature CI](https://github.com/ekkehard-lutz/wallbox-manager/actions/runs/42627437886) and [exact merge CI](https://github.com/ekkehard-lutz/wallbox-manager/actions/runs/42638084085) passed. Merge validation also passed 1,141 Python tests with 94% statement coverage (4,541 statements, 256 missed), Ruff lint and format, JavaScript syntax, 95 card regressions, one headless Chrome layout fixture, five manifest/HACS/localization JSON checks, 113 documentation link and anchor checks and Git whitespace checks. The manifest remains `0.4.0-beta.22`. The push updated only `develop`.

The supported target is current-format v0.4 with a single private-household operator. The audit excludes historical v0.3 and beta imports, downgrade compatibility and registry/Recorder continuity as release requirements. Current-format settings, session/economic state, behavior and truthful HA presentation remain release requirements. The inventory classifies code as it exists at the baseline. Each removal or simplification below is a proposal for independent review and explicit operator approval.

Source locations below are baseline line numbers. Short Python paths resolve under `custom_components/wallbox_manager/`. The audit read all 30 Python modules and inspected the card, registration and service schemas, five metadata/localization JSON files, brand assets, tests and specifications. It combined literal searches, AST enumeration, tracing reads and writes across the config entry and HA Stores, and tracing callbacks and framework entry points. It matched dynamic entity roles and translation keys against their actual producers. It checked the 45 tracked test files as evidence, distinguishing active regression contracts, historical fixtures and test instrumentation. Isolated replay and sizing probes used synthetic state. The audit had no access to operator automation definitions and made no calls to live HA, a station, a vehicle or an inverter.

The historical WBM comparison used `v0.3.2-beta.18` at `87963014c9af73416c438807f523a3da2a98bd22`, particularly `docs/phase-lockout-protocol.md:16–46`. Its separate treatment of atomic lockout responses and confirmed physical phase still matters to F1/F5. The current implementation carries that distinction through OCPP outcomes and canonical observations. Local Stationary source at `279287c3c1d8863e803144eccf773ab3f10889a5` was checked against `ocpp_runtime/transactions.py:132–174,214–237`, `ocpp_runtime/device_model.py:28–44`, `ocpp_runtime/phase_feedback.py:1–38` and `ocpp_runtime/station.py:652–655` for transaction identity, device model and physical feedback. Actual openWB source at `849340ec8d91f4e7cca08a7664cf9ec0187fb496` was checked in `packages/control/chargepoint/chargepoint.py:154–188` for charging eligibility and unplug-driven session behavior. That is an implementation comparison. The Stationary OCPP interface is the contract WBM consumes. Neither source provides an ordered global transaction identifier WBM can use as a retirement watermark.

In the removal and simplification tables, “independent” describes implementation dependencies, not approval status.

## F4 — unreachable branch

In `number.py:178–210`, the restore guard admits only `desired_charging_power` or an `allowed_current_*` role with no current persisted value. The cap branch at lines 192–197 saves the raw restored value, then returns. The code that reaches lines 198–208 therefore handles only `desired_charging_power`. The true arm of the conditional at lines 203–207, which serializes a cap fraction, cannot run. Replacing that conditional with its false arm would preserve behavior. R01 removes the surrounding obsolete desired-power restore entirely, so a separate patch would duplicate the cleanup. Preserve `Fraction` for current Number parsing at lines 83–86 and preserve exact cap storage through the current settings path.

## F6/R4 — terminal transaction IDs

`session.event()` first checks current generation, valid connector scope and epoch, then rejects a transaction ID found in `closed_transactions` (`session.py:67–72`). It adds an ID on Ended or when a newer valid transaction supersedes it (`session.py:77–120`). Schema-2 persistence writes and reloads the whole set (`session.py:279–293,343–350`). The set grows with distinct retired IDs and is rewritten when the session record is saved.

The audited Stationary source creates opaque transaction identifiers and sequences events within each transaction. Connection/boot generations fence transport lifecycles. A timestamp check excludes events before the current epoch, and a per-ID sequence comparison needs retained state for that ID. In a scratch-state probe, a fresh-timestamp, current-generation `Updated` for a retired UUID was rejected with the set present and accepted as live in a copy with the set cleared. A count cap, timestamp cutoff or generation-only check can therefore re-admit a closed ID. Re-admission could reopen WBM session eligibility, including economic budget or NETZ transaction scope.

At two retired IDs per day, 730, 3,650 and 7,300 opaque UUIDs represent roughly one, five and ten years. A compact JSON encoding of the sorted ID list took 28,929, 142,809 and 285,159 bytes respectively. The approximate Python set plus string footprint was 89,194, 412,338 and 1,086,604 bytes. Minimum local sort/encode times in the probe were 0.27, 1.54 and 3.24 ms. These estimates exclude HA Store overhead, fsync and target hardware measurements. The results establish linear growth and do not show a material household-scale release blocker. Keep the set for v0.4. Revisit representation only with a concrete persistence cost or a Stationary contract that permits exact retirement without remembering each opaque ID.
