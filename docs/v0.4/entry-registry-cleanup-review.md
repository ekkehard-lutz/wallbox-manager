## Setup and binding

| Area | Before | After |
| --- | --- | --- |
| Source of the station/EVSE/connector target | Setup combined config-entry data, profiles, historical subentries, saved station references and full registry scopes as candidate targets. | `binding.py` requires the complete explicit target in config-entry data and validates the station identifier and positive canonical EVSE/connector identifiers. Profiles and registry records are checked for conflicts. They never supply a missing target. |
| Config-entry versions and layout | HA's migration callback converted major versions 1 and 2 to 3. Setup could move entities and devices out of old subentries, take a snapshot and remove the subentries. | The HA migration callback accepts major version 3 and returns false for unsupported older versions. HA still rejects newer major versions in its lifecycle. Setup rejects historical subentries before mutation and leaves old options snapshots inert. No conversion, registry reparenting or config-entry rewrite occurs on normal setup. |
| Profile storage | The current `.profiles` store and startup approval logic coexisted with explicit obsolete-key scrubs. | The same scoped store, key format and approval logic remain. A malformed profile target or a scope incompatible with the configured binding fails before setup writes. Existing keys that describe the same scope are tolerated, and the existing canonical string-valued key remains authoritative. Unknown fields, including retired PV delays and phase deviation, stay inert on disk and are not copied into runtime settings. A reload does not rewrite storage to remove them. |
| Entity and device registry | Setup scrubbed selected old capability and control records. It could move registry associations. | Current IDs, user-assigned entity IDs, device identity, labels, disabled status and associations remain on reload. Scoped IDs and station IDs are checked before setup writes, including a current entity linked to a different station device. Retired records are left in the registry. Lazy capability entities are rehydrated only for capability roles the current OCPP device model actually reports. |

The registry decoder is shared by binding validation and lazy sensor registration. The unique ID serializer, observation projection and current device identifiers are unchanged. The decoder distinguishes station IDs from scoped IDs even if a station name matches a family name such as `control`. The OCPP capability mapping moved to the common constants module so discovery and sensor rehydration use the same role names. No wire behavior changed.

R05/R06 remove the `pv_start_delay` and `pv_stop_delay` filters and the historical `phase_switch_deviation_pct` registry scrub. R09 removes historical lookup and repair based on `station_references` and `passive_v04_legacy_subentries`, the remaining capability scrubs and the old `grid_set`, `wake_up_vehicle` and `auto_wakeup_enabled` registry deletions. Existing records for those controls can remain visible as unavailable. Current `grid_set_required`/`grid_set_ready` approval fields, `take_control`, `charge_action`, generic `button.press`, the explicit action service and `charging_enabled` are retained.

## Settings and OptionsFlow

R08 removes early restore-state adoption and the late Number/Select `RestoreEntity` adapters. Current scoped settings win even if HA has an older state with a different value. An absent cap defaults to its reported capability ceiling. Explicit 0 A disables that phase mode. Explicit caps and direction survive reload, and capability changes still normalize the effective limit without modifying the stored cap. Existing exact fractional caps still parse and normalize. An absent direction defaults to `nearest`. Durable NETZ draft/approval and timing retain the existing release retirement semantics. Startup does not grant release, authority or permission.

R10 reads options from the current nested `general` and `regulation` sections only. The HA form, source-selector update and clearing semantics, diagnostics levels 0–3, numeric constraints and `invalid_settings` response are unchanged. Flat data no longer updates any setting. Unloaded-entry options and the nine optional regulation Numbers retain their existing behavior. Old keys in the options store can pass through unchanged without becoming active inputs.

## Validation and review

New current-format tests were run against the Phase A baseline before production edits. Eight passed and nine failed. The failures showed the old restore adoption and flat-options writes, v1/v2 conversion, inference or non-HA errors for missing and invalid targets, and a registry reload failure for a station named `control`. The corresponding cases now pass. The old migration assertions were replaced with rejection and no-mutation checks. Existing assertions for current energy metadata, disabled entity state, exact current caps, durable approval, release retirement and legacy session import remain covered. Registry tests check that obsolete controls and capability sensors stay inert, while current lazy entities retain their identities.

- Full `python -m pytest -q` with the local Stationary source fixture passed 1,170 tests in 295.46 seconds. Statement coverage was 95% (4,462 statements, 222 missed). The five dependency deprecation warnings came from Home Assistant HTTP and Backoff.
- The broader focused suite passed 544 tests. The separate binding/registry/NETZ approval run passed 75. These runs include F1, F3, F5, R1, R2, R3 and the PV transaction rollover.
- Ruff lint and format, JavaScript syntax, 95 card regressions, one headless Chrome fixture, four local links and anchors across the changed documentation, and Git whitespace checks passed. Manifest, HACS metadata, all three localization files and all three service schemas are unchanged.

Source cross-checks used WBM `v0.3.2-beta.18` at `87963014c9af73416c438807f523a3da2a98bd22` (`docs/phase-lockout-protocol.md:16–46`), Stationary `279287c3c1d8863e803144eccf773ab3f10889a5` (`ocpp_runtime/config.py:75–81`, `ocpp_runtime/device_model.py:91–105,193–218` and `ocpp_runtime/transactions.py:166–175,187–207`), and openWB `849340ec8d91f4e7cca08a7664cf9ec0187fb496` (`packages/control/chargepoint/chargepoint.py:154–188`). Stationary routes by station identity and reports explicit EVSE/connector scope. Station-side electrical protection, atomic lockout and physical feedback stay outside the HA registry and settings paths.

Charging policy and Stationary safety ownership are unchanged. Batch 4, including the retired PV and session importers, F3 journal verification, session schema and serialization, the complete closed-transaction ID set, and new-transaction rollover, is unchanged. No new polling, controller or safety logic was added. No physical installation was contacted, and no version, release, tag or deployment changes were made.

Independent review should focus on the fail-before-write paths and existing current registry associations. An unsupported entry with missing binding data, a historical subentry or conflicting registry data requires operator correction. The software tests use simulated HA and OCPP peers. They do not establish field behavior on a physical installation.
